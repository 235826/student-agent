# 第三阶段：确定性排程

入口为“学习计划”。先在设置页添加每周可用时间及休息窗口，再为任务填写预计用时；选择排程起止时间和计划块长度后生成草稿。草稿不会影响当前计划。确认采用时可接受有未排工时的部分计划，页面会明确提示。

## 算法与边界

排程针对本工作区所有未删除且状态为待开始或进行中的任务。单次范围最多 31 个实际日（744 小时），最多 500 项未完成任务，开始时间必须在未来。按依赖拓扑顺序，从当前可处理集合中按截止时间、优先级、创建时间和 ID 稳定排序；相同输入生成相同计划块。

任务按完整预计用时安排。当前没有实际耗时记录，进行中任务不会自动扣除已经完成的工时；需要用户调整估时，后续工作日志阶段再引入剩余工时计算。没有估时的任务不猜测时长，单独列出待补充原因。父子关系不自动形成先后约束。

排程使用一分钟粒度，只使用完整落在可用窗口内的分钟；与休息窗口或事件相交的分钟均保守处理。计划块默认 25–90 分钟，可调整；最后一个计划块可小于最小长度。不自动插入休息，用户设置的休息窗口始终扣除。

每周窗口按用户时区解释，时间点以 UTC 毫秒保存。夏令时跳跃产生的不存在分钟不会使用；回拨产生的两个实际分钟按各自 UTC 时间点处理。更改时区不移动已采用计划块，但下一次生成会按新时区解释每周窗口。

事件一律不被移动或改写。明确跳过的课程不占个人时间。任务与事件、其他任务重叠时，检查该分钟内所有活动的每一对组合，只有用户确认的兼容规则可以授权；依赖任务始终串行。只有前置任务全部排完，后续任务才会在其完成时间之后安排；前置已完成则直接满足依赖。已取消、已删除、缺少估时或未排完的前置会阻止后续任务。

这是稳定的贪心可行解，不保证全局最优，也不自动推断个人高效时段。每项任务显示已排工时、未排工时和原因；缺少窗口、缺少估时、截止时间已过以及前置阻塞分别提示，其他不足说明时段容量、冲突或最小块长度限制。不会把时间不足伪装为全部排完。

## 计划版本与确认

每份计划保存计划块（含当时任务标题）、结果报告、来源数据版本、生成时的当前计划 ID，以及新增/移除计划块明细。采用会替换整个当前计划，不仅替换所选日期范围；界面在生成和确认处均说明。旧计划成为历史版本，继续可查看。时间移动表示为移除旧块、增加新块，页面可展开查看具体任务和起止时间。

生成使用幂等键，网络重试不会产生重复草稿。同一已采用版本重复确认返回现有结果；历史版本不能直接重新采用。确认前检查来源版本、当前计划 ID 和排程开始时间；任一变化或开始时间已过则拒绝采用，要求重新生成。所有会影响排程的任务、事件、规则及设置操作都会更新来源版本。

确认与其他写操作共用 SQLite 写事务，数据库另设每工作区最多一个当前计划的唯一索引。两个草稿并发采用时仅一个成功。任务或规则变化后，已采用计划仍保留并显示“依据已变化”或“时间已过”提示，不自动替换用户计划。首页日历展示当前已采用计划块；计划页可切换草稿和历史版本。计划页事件层使用当前课表，历史版本的任务块和报告保持原快照。

## 接口与迁移

- `POST /api/v1/plans`：生成草稿；请求含起止时间、块长度与幂等键。
- `GET /api/v1/plans`：本工作区计划版本与过期状态。
- `GET /api/v1/plans/current`：当前计划，没有时返回 null。
- `POST /api/v1/plans/{id}/adopt`：显式 `confirmed=true` 后采用。

迁移 `0003` 新增计划快照表，不改写原有业务数据。升级前使用 SQLite backup API 创建一致性备份；禁止直接 downgrade 删除计划数据。回退需停服、另存新数据库，再以升级前备份配合旧版本程序恢复。

AI 导入、工作日志、自动重排、后台提醒以及优化求解器均未包含在本阶段。
